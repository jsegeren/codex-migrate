Codexを新しいMacへ
安全に移行する。

ChatGPTに同じアカウントでサインインしても、Codexのローカル会話、スキル、Gitのworktree、未コミットの変更がすべて新しいMacに現れるとは限りません。このガイドでは、移すべきデータと、コピーしてはいけない端末固有データを分けて説明します。

Codex Migrateは、OpenAI Codex（ChatGPTデスクトップアプリ内のCodexを含む）のローカル作業環境を、SSH経由でMac間に直接転送する独立したオープンソースツールです。通常のChatGPTクラウド会話、アカウント間の会話履歴、ChatGPTの全モードを移行する製品ではありません。

結論：~/.codexを丸ごとコピーしない

~/.codex全体をそのままコピーすると、会話だけでなく、古いMacの認証情報やinstallation_idなどの端末固有データまで新しいMacへ持ち込む可能性があります。その結果、2台のMacが同じCodex端末として扱われたり、Remote Controlの接続先が上書きされたりする事例が報告されています（OpenAI Codexのissue #37106、issue #33830）。

新しいMacでは先にCodexをインストールし、一度起動してサインインします。そのMac自身のログイン情報と端末IDは保持し、移行可能な会話・設定・作業ファイルだけを転送するのが安全です。

何を移行するのか

  • ローカルに保存されたCodexの会話とアーカイブ済みタスク
  • Codexの設定、プロジェクト構成、ルール、メモリ、オートメーション
  • 個人用・プロジェクト用のカスタムスキル
  • 選択したワークスペース内のGitリポジトリ、ローカルブランチ、タグ、stash、worktree
  • 未コミット・未追跡のファイルなど、GitHubへpushされていない作業

git cloneだけでは、pushしていないブランチ、stash、未追跡ファイル、Codexのローカル会話は戻りません。逆に、通常のMacデータをすべて移したい場合はAppleのMigration Assistantの方が目的に合うことがあります。

転送しないもの

  • 古いMacの~/.codex/auth.json
  • 古いMacの~/.codex/installation_id
  • ~/.ssh内の秘密鍵
  • 実行中だけ必要なsocket、lock、log、cache
  • 明示的に選択していないホームフォルダ内のデータ

ただし、選択したリポジトリ内にAPIキーや秘密情報が保存されていれば、そのファイルも転送対象になります。実行前に選択内容を確認してください。

Wi‑Fi、USB‑C、Thunderboltのどれを使う？

転送自体はSSHで行います。同じWi‑Fi上でも利用できます。USB‑CまたはThunderboltケーブルを使う場合は、そのケーブルとMacの設定でネットワーク接続が成立している必要があります。充電専用・低速のUSB‑Cケーブルでは、Thunderboltより遅い、または接続経路として使えないことがあります。

Codex Migrateは、信頼済みの移行先Macが公開するプライベートアドレスだけを確認し、到達可能な経路を小さな速度テストで比較します。LAN全体をスキャンしたり、SSHのホスト鍵検証を無効にしたりはしません。

安全な移行手順

  1. 古いMacを消去せず、別のバックアップも残します。
  2. 新しいMacにCodexをインストールし、起動して自分のアカウントで一度サインインします。
  3. 新しいMacで、移行先ユーザーだけにRemote Loginを許可します。
  4. SSHのホストフィンガープリントを確認し、移行元・移行先・選択フォルダ・必要容量を事前検査します。
  5. 隔離された場所へ転送をステージします。中断しても同じ条件で再実行すれば、完了済みデータを再利用できます。
  6. 両方のMacでCodexを終了し、移行先バックアップの内容検証が成功してから置き換えます。
  7. 新しいMacで重要な会話を開き、Git status、ブランチ、worktree、スキル、未完了ファイルを確認します。
  8. 実際に新しいMacで作業できるまで、古いMacと独立バックアップを保持します。

よくある質問

2台のMacを継続的に同期できますか？

いいえ。Codex Migrateは一度の移行または復旧用で、2台で同時に変更された会話やリポジトリをリアルタイムに統合する製品ではありません。

新しいMacのCodexログインは消えませんか？

移行先Macで先に作成された認証情報とinstallation_idを保持し、移行後も変わっていないことを検証します。

転送が途中で止まったら？

ステージングは再開可能です。置き換え処理が中断した場合は、保存済みのトランザクションとバックアップを検査してから復旧します。中断したデータを「成功」とは扱いません。
